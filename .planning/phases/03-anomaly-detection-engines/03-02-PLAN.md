# Plan 03-02: Exclusion, Duplicate Parcel, Statistical & Temporal Engines + Pipeline Orchestrator

## Objective
Implement the final 4 anomaly detection engines (Exclusion, Duplicate Parcel, Statistical/Geographic, Temporal Spike) and wire them all together into a synchronous `AnomalyPipeline` orchestrator that runs on every new application submission, returning a unified list of `AnomalyFlagResult` objects to the caller.

## Context
- Exclusion checks the `exclusion_master` table for known disqualified individuals by `aadhaar_ref`.
- Duplicate Parcel scans ALL existing `PMKisanApplicationDetails` for the same `parcel_id` with a different `application_id`.
- Statistical Engine queries `VillageProfileMaster` to compute the current application rate vs. the historical cultivator baseline for the village.
- Temporal Engine queries `EventCalendarMaster` for upcoming events within 48 hours and counts recent district submissions to detect surge patterns.
- `anomaly_pipeline.py` imports and calls all 7 engines in order, collects all flags, and returns a `PipelineResult` object.
- The pipeline is called inline from `POST /api/applications/pm-kisan` immediately after the application is persisted.

<action>
Create `backend/app/services/duplicate_parcel_engine.py` implementing `run(details, db) -> List[AnomalyFlagResult]`:

1. Query `PMKisanApplicationDetails` for other rows with `parcel_id == details.parcel_id` and `application_id != details.application_id`.
2. Also collect the Aadhaar refs of those conflicting applicants.

5. Evidence: `{"conflicting_application_ids": [...], "distinct_aadhaar_refs": N}`.

<task id="3">
<title>Implement Statistical & Geographic Engine</title>
<action>
Create `backend/app/services/statistical_engine.py` implementing `run(details, db) -> List[AnomalyFlagResult]`:

1. Query `VillageProfileMaster` for `village_code == details.village_code`.
2. If no baseline record found, return empty list (can't compute density without baseline).
3. Count current approved/submitted applications in the same village from `PMKisanApplicationDetails` joined with `Application` (excluding the current application if it is already persisted): `current_village_count`.
4. Baseline = `master.historical_beneficiary_count` (fallback to `master.cultivator_count_estimate` if 0).
5. If baseline == 0, return empty list.
6. Compute `ratio = current_village_count / baseline`.
7. If `ratio > 2.5` → `STAT_VILLAGE_DENSITY_HIGH` (High, 40). Rationale: f"Village {details.village_code} shows {ratio:.1f}x application density vs historical cultivator baseline ({current_village_count} applications, baseline {baseline})".
8. If `ratio > 1.75` → `STAT_VILLAGE_DENSITY_MEDIUM` (Medium, 25). Rationale same.
9. Evidence: `{"village_code": "...", "current_count": N, "baseline_count": N, "ratio": ratio}`.
</action>

<task id="4">
<title>Implement Temporal Spike Engine</title>
<action>
Create `backend/app/services/temporal_engine.py` implementing `run(details, db) -> List[AnomalyFlagResult]`:

1. Get current timestamp `now = datetime.datetime.utcnow()`.
2. Query `EventCalendarMaster` for events in `details.district_code` where `event_date` is within the next 48 hours (`now <= event_date <= now + timedelta(hours=48)`).
3. If no upcoming events found, return empty list.
4. Define 14-day baseline window: `window_start = now - timedelta(days=14)`.
5. Count all applications in `details.district_code` from the last 14 days (`Application.submitted_at >= window_start`) joined via `PMKisanApplicationDetails.district_code`. Compute `baseline_rate_per_day = total_14d_count / 14.0`.
6. Count applications submitted in the last 48 hours from the same district: `recent_48h_count`.
7. `expected_48h = baseline_rate_per_day * 2`.
8. If `expected_48h == 0`, return empty list.
9. Compute `surge_ratio = recent_48h_count / expected_48h`.
10. If `surge_ratio > 5.0` → `TEMPORAL_SPIKE_HIGH` (High, 40). Rationale: f"District {details.district_code} shows {surge_ratio:.1f}x submission surge in 48h before milestone event on {event_date}".
11. If `surge_ratio > 3.0` → `TEMPORAL_SPIKE_MEDIUM` (Medium, 25). Same rationale.
12. Evidence: `{"district_code": "...", "recent_48h_count": N, "expected_48h": ..., "surge_ratio": ..., "upcoming_event_date": "..."}`.
</action>

<action>

1. Define `PipelineResult` dataclass: `flags: List[AnomalyFlagResult]`, `engines_run: List[str]`, `error_log: List[str]`.
2. Implement `run_pipeline(details: PMKisanApplicationDetails, db: Session) -> PipelineResult`:
   - Import all 7 engines: `identity_engine`, `land_engine`, `bank_engine`, `exclusion_engine`, `duplicate_parcel_engine`, `statistical_engine`, `temporal_engine`.

   - Aggregate all returned `AnomalyFlagResult` lists into `flags`.
   - Return `PipelineResult(flags=all_flags, engines_run=[...], error_log=[...])`.
