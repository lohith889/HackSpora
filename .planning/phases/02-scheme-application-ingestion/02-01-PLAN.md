# Plan 02-01: Scheme Metadata Specification & Key Generation Utilities

## Objective
Implement scheme metadata endpoints (`GET /api/schemes/PM_KISAN/fields`) providing field specifications, section schemas, validation constraints, and helper functions for composite key generation (`parcel_id` and `bank_account_ifsc_key`) and identifier normalization.

## Context
- The KisanGuard Portal requires a dynamic scheme specification endpoint so that client forms know the exact fields, data types, validation regexes, and sections required for PM-KISAN.
- Derived identifiers must be consistent across the entire platform:
  - `parcel_id`: `{state_code}-{district_code}-{tehsil_code}-{village_code}-{khata_number}-{plot_number}` (uppercase)
  - `bank_account_ifsc_key`: `{bank_account_number}-{ifsc_code}` (uppercase)
- Validation constraints:
  - Mock OTP: `123456`
  - Aadhaar format: 12 numeric digits
  - IFSC code: 11 characters `^[A-Z]{4}0[A-Z0-9]{6}$`
  - Land area: positive float > 0
  - Allowed document extensions: `.pdf`, `.jpg`, `.jpeg`, `.png` (max 5MB)

## Tasks

<task id="1">
<title>Add scheme and composite key utility functions</title>
<action>
Create `backend/app/utils.py` with the following utility functions:
1. `generate_parcel_id(state_code: str, district_code: str, tehsil_code: str, village_code: str, khata_number: str, plot_number: str) -> str`:
   Formats and uppercases components joined by hyphens.
2. `generate_bank_ifsc_key(bank_account_number: str, ifsc_code: str) -> str`:
   Formats and uppercases `{bank_account_number.strip()}-{ifsc_code.strip().upper()}`.
3. `validate_aadhaar_format(aadhaar: str) -> bool`:
   Checks if cleaned Aadhaar is exactly 12 numeric digits.
4. `validate_ifsc_format(ifsc: str) -> bool`:
   Regex check against `^[A-Z]{4}0[A-Z0-9]{6}$`.
5. `validate_mock_otp(otp: str) -> bool`:
   Checks if OTP is `"123456"`.
6. `get_citizen_status_message(status: str) -> str`:
   Returns citizen-safe status message (e.g. `SUBMITTED` -> "Application received and under preliminary verification", `AUTO_CLEARED` -> "Application verified successfully and queued for subsidy disbursement", `UNDER_REVIEW` -> "Application documents are currently being cross-referenced with state land records", `ACTION_REQUIRED` -> "Additional document verification requested by scheme officer", `PAYMENT_HELD` -> "Application verification pending officer clearance").
</action>
<verify>
Unit test or python import check verifying that functions format keys and validate formats properly.
</verify>
<done>
`backend/app/utils.py` created and tested for key generation and validation logic.
</done>
</task>

<task id="2">
<title>Define Scheme and Ingestion Pydantic Schemas</title>
<action>
Update `backend/app/schemas.py` to add:
1. `SchemeFieldSpec`: schema describing an individual field (name, label, type, required, validation_regex, options, help_text).
2. `SchemeSectionSpec`: schema describing a form section (section_id, title, description, fields).
3. `SchemeMetadataResponse`: response model for `GET /api/schemes/{scheme_code}/fields` with `scheme_code`, `scheme_name`, `version`, `sections`, `allowed_mime_types`, `max_file_size_mb`.
4. `ApplicationSubmissionResponse`: citizen-safe response with `application_id`, `scheme_code`, `status`, `citizen_status_message`, `submitted_at`, `parcel_id`, `aadhaar_masked`.
5. `CitizenApplicationSummary`: list item for `GET /api/applications/my` with `id`, `scheme_code`, `status`, `citizen_status_message`, `submitted_at`, `farmer_name`, `parcel_id`.
6. `CitizenApplicationDetail`: detailed view for farmer with applicant details, land details, bank details (masked), land document URL, citizen status message, but strictly WITHOUT `risk_score`, `confidence_level`, or `anomaly_flags`.
7. `AdminApplicationDetail`: full view for scheme officer including applicant details, master keys, raw risk score, confidence level, anomaly report, and audit logs.
</action>
